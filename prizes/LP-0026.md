# LP-0026: Simple Forum App [OPEN]

**`Status: Open`**
**`Logos Circle: N/A`**

## Overview

Public forum to allow open and educational discussion of ideas whilst retaining fundamental rights to privacy.
With increasing surveillance, personal identification, and targeted retaliation on social media, the internet is losing its ability for people to freely speak their mind and learn rapidly from each other. A forum with privacy at its core provides a safe space for people to exchange ideas without preempting censorship/oppression, eg politics. An important muscle to work to retain free-thinking and not accept capture by corporations that seek to isolate individuals and limit free speech.

## Motivation

Enable people to freely discuss ideas on any topic. Filling the gap of tools that allow free and open communication that aims to protect the privacy of users and allay the fear of censorship.
This prize mechanism works well to encourage developers to build for interesting domains, and possibly make unique tech choices.

## Success Criteria

### Functionality

- [ ] The application does not depend on any centralised server or service.
- [ ] Forum data uses the Logos stack: **Logos Storage** for storage and data availability, **Logos Delivery** for publishing data, and **Logos Chat** for end-to-end encrypted peer-to-peer coordination.
- [ ] A person can post from one or more accounts.
- [ ] A person can create a topic and reply to an existing one.
- [ ] A reply can show a unique id, an alias (with or without that id), or no id at all.
- [ ] The submission documents the identity model it ships — one persistent identity, manual rotation, or automated rotation — and what that choice reveals about the author. The app implements the model it documents.

### Usability

- [ ] A Logos Basecamp app GUI, with local build instructions, that loads in Basecamp.
- [ ] A pre-built release in a [Logos module catalog](https://github.com/logos-co/logos-modules-release-base), so the app can be installed in Basecamp without a local build.
- [ ] The forum is usable by a non-expert: coherent navigation across topics, browsing messages, and clear error and pending states. Evaluators use it as an ordinary user would and judge the overall impression.

### Reliability

- [ ] If the app is offline when a message would have been received, it can obtain that message later.
- [ ] If sending a message fails, the text stays on the device so the person can retry.

### Performance

- [ ] The app does not flood the network. Traffic is limited to forum messages a person publishes or fetches.

### Supportability

- [ ] The design is sound, and functionality another Logos app could reuse is separated from this forum's UI.
- [ ] CI is green on the default branch.
- [ ] A README documents end-to-end usage: how to build and load the app in Basecamp, and how to create a topic, reply, and retry a message that failed to send.
- [ ] A recorded video demo of the end-to-end flow is included in the submission.

### Adoption

> Real use of a submission, in addition to the criteria above. A headline count is not the bar (see [Terms & Conditions](../TERMS.md)). Evaluators read the forum. Activity that is clearly manufactured — fresh accounts, sock-puppets, a single burst, or AI-generated threads — does not count.

- [ ] Realistic topics and organic conversations are underway, from people other than the submitting team. There is more than one topic, with replies, and the activity is spread over time rather than posted in one burst. Evaluators check that the conversations are genuine.

## Scope

### In Scope

Forum described above including the user experience (feel/polish), and adoption via meaningful use.

### Out of Scope

The developer can choose what to include or not, beyond basic forum functionality. This will help builders to differentiate themselves and their apps to stand out.
- Use of the blockchain module is considered out of scope for this LP so that focus prioritises core forum functionality. This may be considered in a future LP.

Open to any individual or team. Submissions must be original work. Teams must hold the rights to all submitted code and agree to dual-license it under the MIT License and Apache License 2.0.

## Submission Requirements

- A narrated video walkthrough demo is always required (see [demo requirements](../README.md#evaluation-policies)). The demo should specifically showcase and discuss:
  - End-to-end usage of the solution, from setup through using the app in all major user scenarios.
  - Successful execution of all core functionality, with relevant UI output visible (state changes, error handling).
  - Integration with the Logos stack (Logos Storage, Logos Delivery, and Logos Chat).
  - Any features addressing explicit evaluation or success criteria (error cases, reliability under failure, compliance with FURPS requirements).
  - Unique or innovative design choices, including the identity model, with a brief discussion during the demo.
  - Anything else evaluators should notice, such as how the app avoids flooding the network.
- The demo must make it easy for evaluators to verify that the implementation meets the stated criteria.
- Evidence for the Adoption criterion: where to read the forum, and enough context for an evaluator to judge that the topics and conversations are genuine.
- Submissions must include a FURPS self-assessment as part of the solution (see [solution template](../solutions/LP-0000.md)).

## Evaluation Process

Submissions are evaluated first-come-first-served against the success criteria and the **Adoption** section. The first submission that meets all of them wins.

Evaluators will independently clone the repository and run the application from a clean environment; the application must run without modification. Evaluators may also ask technical follow-up questions to verify authorship and understanding of the implementation.

The following policies apply to all prizes (see [evaluation policies](../README.md#evaluation-policies)):

- **Submissions:** each builder (or team) is allowed a maximum of **3 submissions** per prize, with at most **one submission/review per week**.
- **Feedback:** initial evaluation feedback is limited to a pass/fail indication against the success criteria and the **Adoption** section.
